全18話で、GitとGitHubの基礎を一周します

第1〜3話は公開済みです。第4話からは、GitHub Actionsが毎朝1話ずつ、自動で公開します。GitHub上の作業履歴がない日でも、用意した順番どおりに進むため、途中で止まりません。

Git基礎第1話 Gitってなに？＝作業のセーブ機能
——スカイブルーの世界。Gitさんは、自分が何者かを思い出せずにいた。
Gitさん
神様…。おれ「Git」って名前だけど、結局なにをする者なの？
神様
ふむ。ひとことで言えば、お前は「作業のセーブ機能」じゃ。
Gitさん
セーブ…？ゲームの、あのセーブ？
神様
そうじゃ。文章でもコードでも、区切りのいいところで「ここまで！」と記録を残す。それがお前の力じゃ。
GitHub氏
へぇ。じゃあ失敗しても、前のセーブに戻れるってこと？
神様
その通り。だから安心して挑戦できる。消えて困るものを、時間ごと残せるんじゃ。
Gitさん
なるほど…！おれ、けっこう頼れるやつだったんだ。
神様
図で見るとこうじゃ。作業して、節目でセーブ。これを繰り返すだけ。
Git基礎第2話 コミット＝セーブする
翌朝。Gitさんは「セーブのやり方」を知りたくなった。
Gitさん
神様、セーブって具体的にどうやるの？
神様
その1回のセーブを「コミット」と呼ぶ。今の状態を写真に撮って、名前を付けて保存するイメージじゃ。
GitHub氏
名前？
神様
「ここで何をしたか」を一言添える。例えば『トップページの文言を修正』のようにな。
Gitさん
あとで見たとき、何のセーブか分かるように…！
神様
その通り。コミットが積み重なると、作業の歴史そのものになる。
GitHub氏
日記みたいだね。
神様
よい例えじゃ。1コミット＝1ページの日記。図を見てみよ。
GitHub基礎第3話 GitHub＝みんなで見られる保管庫
セーブを覚えたGitさん。でも、GitHub氏はまだ自分が何者か分からない。
GitHub氏
神様…。おれ「GitHub」だけど、Gitと何が違うの？
神様
Gitが手元でのセーブなら、GitHubは「そのセーブを、みんなが見られる場所に置く保管庫」じゃ。
Gitさん
おれのセーブを、ネットに置いておく所…？
神様
そう。自分のパソコンが壊れても大丈夫。仲間と一緒に見て、直せる。
GitHub氏
だからか…！なんかおれの中に、おれじゃない誰かがたくさんいる気がしてたんだよー。
神様
team AICのホームページも、GitHubに置いたものが世界に公開されておる。
Gitさん
手元でセーブ（Git）、ネットで共有（GitHub）。コンビなんだね。
神様
その通り。二人で一人前じゃ。図を見よ。
GitHub基礎第4話 リポジトリ＝プロジェクトの保管箱
——GitHub氏の部屋には、たくさんの箱が並んでいた。
GitHub氏
この箱は何？ 中にファイルや記録が入っているんだけど。
神様
それはリポジトリ。ひとつのプロジェクトに関わるファイルと履歴をまとめる保管箱じゃ。
Gitさん
ホームページ用の箱、メモ用の箱、と分ければ迷わないね。
神様
その通り。何のための箱かを説明できる名前にすると、仲間も未来の自分も助かる。
今回のポイントリポジトリは、ファイル・履歴・共同作業の記録を一つの目的でまとめる単位です。10分で試すこと
  • team AICのリポジトリを開き、ファイル一覧と履歴一覧を見比べる。
  • リポジトリ名から目的を一言で説明してみる。

確認事項：公開リポジトリの内容は誰でも見られます。公開してよい内容だけを置きます。

GitとGitHubの関係第5話 手元とネットの二つの場所
——GitさんとGitHub氏は、同じ記録を持っているようで少し違っていた。
Gitさん
ぼくの手元の記録と、GitHub氏のところの記録は同じなの？
神様
似ているが、別の場所にある。手元はローカル、GitHub側はリモートと呼ぶんじゃ。
GitHub氏
だから、手元で作っただけではぼくの箱には届かないんだ。
神様
そうじゃ。二つの場所の違いを知ることが、Git/GitHubで迷わない第一歩になる。
今回のポイントローカルは自分のパソコン、リモートはGitHub上の保管場所です。10分で試すこと
  • 『手元だけにある変更』と『GitHubにある変更』を紙に二列で書く。
  • どちらを他の人が見られるか答える。

確認事項：GitHubへ送る前の手元の変更は、まだ公開版には反映されません。

Git操作第6話 git status＝まず現在地を見る
——Gitさんは急いで出発しようとして、神様に止められた。
Gitさん
すぐ保存して送ればいいんだよね？
神様
待つのじゃ。最初に今の状態を見る。そこで使うのが git status じゃ。
GitHub氏
変更したファイルや、まだ保存されていない変更が分かるの？
神様
そうじゃ。道に出る前に地図を見るようなもの。慌てた操作を減らせる。
今回のポイントgit statusは、変更・保存準備・未追跡のファイルを確認する最初のコマンドです。10分で試すこと
  • 作業の前後に git status を実行する。
  • 表示されたファイル名を、意図した変更か確認する。

確認事項：意味が分からない表示のまま次の操作へ進まないことが、安全な基本です。

Git操作第7話 git add＝保存する変更を選ぶ
——机の上には、保存したいメモと、まだ途中のメモが混ざっていた。
Gitさん
変えたものを全部まとめてセーブしていい？
神様
まず git add で、今回のコミットに入れる変更を選ぶんじゃ。
GitHub氏
途中の下書きまで混ぜなくていいんだね。
神様
その通り。目的の違う変更を分けると、後から理由をたどりやすい。
今回のポイントgit addは、次のコミットに含める変更を選ぶ準備です。10分で試すこと
  • git statusで変更を確認する。
  • 今回の目的に関係するファイルだけを git add する。

確認事項：よく分からないファイルをまとめて追加しないこと。まず内容を確認します。

Git操作第8話 push＝手元のセーブをGitHubへ届ける
——コミットを作ったGitさんは、GitHub氏へ連絡したくなった。
Gitさん
手元でコミットしたよ。GitHub氏の箱にも入る？
神様
まだじゃ。git pushで、手元のコミットをリモートへ送るんじゃ。
GitHub氏
届けば、ぼくの画面でも履歴として見られるんだね。
神様
そうじゃ。pushの成功表示を確認してから、GitHubの画面でも内容を見るのじゃ。
今回のポイントgit pushは、ローカルのコミットをGitHub上のブランチへ送る操作です。10分で試すこと
  • コミット後に git push を実行する。
  • GitHubのコミット一覧を更新し、同じメッセージが見えるか確認する。

確認事項：pushは公開やmainへの反映と同義ではありません。送った先のブランチを必ず確認します。

Git操作第9話 fetch / pull＝始める前に最新を受け取る
——GitHub氏の箱には、Gitさんが知らない新しい記録が増えていた。
GitHub氏
ほかの人が先に更新しているかもしれないよ。
Gitさん
じゃあ、作業を始める前に見に行く必要があるね。
神様
git fetchは最新情報を受け取る操作、git pullは受け取って手元へ反映する操作じゃ。
神様
まず状態を確認し、何が変わるか分かったうえで取り込むのが大切じゃ。
今回のポイントfetchは確認用に最新情報を受け取り、pullは手元の作業にも取り込む操作です。10分で試すこと
  • 作業前に git fetch origin main を実行する。
  • 取り込む前に git status と変更内容を確認する。

確認事項：未保存の変更があるとpullで問題が起きやすくなります。作業を区切ってから実行します。

共同作業第10話 ブランチ＝本番を守る別の作業道
——一本の道に全員が集まり、Gitさんは身動きが取れなくなっていた。
Gitさん
本番の道で直接直すと、途中の変更まで見えてしまうね。
神様
そこでブランチを作る。本番から分かれた、自分の作業用の道じゃ。
GitHub氏
完成するまで別の場所で試せるんだ。
神様
そうじゃ。終わったら確認して、本番のmainへ取り込む。
今回のポイントブランチは、公開版のmainを守りながら変更を進めるための作業単位です。10分で試すこと
  • 作業用ブランチ名に、目的が分かる言葉を付ける。
  • mainで直接直す場面と、ブランチで進める場面を考える。

確認事項：ブランチ名に個人情報や機密情報を書かないようにします。

共同作業第11話 Pull Request＝変更を見てもらう提案書
——作業道を歩き終えたGitさんは、本番の道へ戻る前に立ち止まった。
Gitさん
できたからmainへ入れていい？
神様
その前にPull Requestを作る。『この変更を見て、取り込みませんか』という提案書じゃ。
GitHub氏
何を変えたか、画面で比べながら見られるんだね。
神様
そうじゃ。急いで公開版を変えず、確認するための場所を作る。
今回のポイントPull Request（PR）は、ブランチの変更をmainへ取り込む前に確認する提案です。10分で試すこと
  • PRのタイトルに『何を変えるか』を書く。
  • 説明に『目的』『変更内容』『確認したこと』を短く書く。

確認事項：PR作成はmainへの反映ではありません。確認の入口です。

共同作業第12話 レビュー＝取り込む前の読み合わせ
——神様は、Pull Requestを静かに読み始めた。
GitHub氏
PRを作ったら、すぐマージしていい？
神様
まずレビューじゃ。変わった箇所、目的、表示、影響を確かめる。
Gitさん
間違いを探すだけじゃなく、意図どおりかを確かめるんだね。
神様
その通り。小さな確認が、公開後の困りごとを減らす。
今回のポイントレビューは、変更の正しさ・意図・影響を確認する作業です。10分で試すこと
  • Files changedで変更箇所を上から読む。
  • 『利用者にどう見えるか』を一つ確認する。

確認事項：自動チェックが通っても、文章や見た目の確認は別に必要です。

共同作業第13話 Merge と Confirm merge＝公開版へ取り込む
——確認を終えた三人の前に、二つのボタンが現れた。
Gitさん
Merge pull requestを押すのが、取り込む操作？
神様
そうじゃ。そしてConfirm mergeは、その内容と記録メッセージで本当に取り込む最終確認じゃ。
GitHub氏
二段階なのは、うっかり本番を変えないためなんだね。
神様
その通り。確認後にmainへ入り、公開の仕組みがその変更を使えるようになる。
今回のポイントMergeは変更をmainへ取り込む操作、Confirm mergeはその実行を確定する最終操作です。10分で試すこと
  • マージ前にPRの目的と変更ファイルをもう一度見る。
  • マージ後にmainの履歴へ記録が入ったことを確認する。

確認事項：マージ後も公開反映まで時間がかかる場合があります。デプロイ状況を確認します。

トラブル対応第14話 コンフリクト＝同じ場所の違う変更を整える
——二人が同じ文章を別々に書き換え、Gitさんは困ってしまった。
Gitさん
同じ場所に二つの変更があるって言われた。どっちが正しいの？
神様
それがコンフリクト。Gitは勝手に選ばず、人に意図を聞いているんじゃ。
GitHub氏
片方を消す前に、両方の目的を確かめるんだね。
神様
そうじゃ。迷ったら作業を止め、変更前後とPRを見直してから整える。
今回のポイントコンフリクトは異常ではなく、同じ箇所への異なる変更を人が判断する必要がある状態です。10分で試すこと
  • 競合したファイル名と、競合した行を確認する。
  • 分からない場合は無理に確定せず、変更の意図を確認する。

確認事項：『oursを採用』などの操作は内容を理解してから。機械的に選ぶと必要な変更を失うことがあります。

自動化第15話 GitHub Actions＝決まった作業を自動で動かす係
——毎朝同じ作業をしている神様の前に、小さな自動係が現れた。
GitHub氏
毎回同じ確認をするなら、誰かに頼めないかな？
神様
GitHub Actionsがその係じゃ。決めた時刻や変更をきっかけに、同じ手順を自動で実行する。
Gitさん
このお勉強会の毎日更新も、その係がしているんだね。
神様
そうじゃ。ただし自動化にも、何を実行するかを書いた設計図が必要じゃ。
今回のポイントGitHub Actionsは、テスト・同期・公開準備などの定型作業をGitHub上で自動実行する仕組みです。10分で試すこと
  • リポジトリのActionsタブを開く。
  • 実行履歴で『いつ、何が、成功したか』を確認する。

確認事項：自動化の失敗は見えにくいことがあります。実行結果と通知の確認を運用に入れます。

公開第16話 GitHub Pages＝GitHubからサイトを公開する場所
——GitHub氏の保管箱から、世界へ続く小さな扉が開いた。
GitHub氏
ファイルを置いただけで、どうしてホームページになるの？
神様
GitHub Pagesが、指定されたファイルをWebサイトとして届けているからじゃ。
Gitさん
mainに入った記録が、公開サイトにつながることもあるんだね。
神様
その通り。だから公開前の確認と、公開後に実際の画面を見ることが大切じゃ。
今回のポイントGitHub Pagesは、リポジトリのHTMLなどをWebサイトとして公開できる機能です。10分で試すこと
  • 公開サイトをスマートフォン幅でも開く。
  • リンク・文章・画像が意図どおりか確認する。

確認事項：公開サイトは広く見られます。住所・連絡先・認証情報などを不用意に載せません。

安全第17話 秘密情報を守る＝GitHubに置かないもの
——GitHub氏の箱に、鍵のかかったメモが混ざりそうになった。
GitHub氏
このパスワードやAPIキーも、記録しておけば便利かな？
神様
いかん。公開リポジトリに秘密情報を置いてはならぬ。消しても履歴に残るおそれがある。
Gitさん
じゃあ安全に自動化するにはどうするの？
神様
GitHub Secretsのような、公開ファイルとは別の安全な保管場所を使うのじゃ。
今回のポイントパスワード、APIキー、トークン、個人情報はコードや公開履歴に入れません。10分で試すこと
  • 公開予定の変更に秘密情報がないか見直す。
  • 設定値を置く場所と公開ファイルを分ける。

確認事項：秘密情報を誤って公開した疑いがあるときは、削除だけで済ませず、その値を無効化・再発行します。
